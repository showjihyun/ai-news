## 클로드 코드, 내 커밋에서 이름 뺀다

인도 출신 개발자 구프타가 1년간 지키던 원칙을 뒤집었다. 자신의 블로그에서 "클로드 코드를 깃 커밋 공동저자에서 빼겠다"고 밝혔다. 해커뉴스에서 18점, 댓글 38개를 모으며 논쟁이 번졌다.

기존 입장은 투명성이었다. LLM 사용 사실을 리뷰어에게 알리려 공동저자 표기를 시작했다. 생각이 바뀌었다. 이제는 LLM 사용이 당연한 시대다.

**목수가 톱 이름을 작품에 새기지 않듯, 도구 이름을 커밋에 남길 이유가 없다.**

## 책임 회피 수단이 될 수 있다

구프타가 지적한 핵심은 책임 전가다. 공동저자가 있으면 실수 발생 시 "AI가 그랬다"고 변명하기 쉽다. 몇 년 전 구글이나 스택오버플로를 공동저자로 올리지 않았듯, 지금도 마찬가지여야 한다.

그는 "내 이름으로 나가는 작업물이면 온전히 내가 책임진다"고 못 박았다. 버그는 LLM 이전에도 있었고, 검증 의무는 도구가 바뀌어도 변하지 않는다.

**이 대목이 걸린다.** 도구 탓을 위한 면죄부가 공동저자 표기 뒤에 숨어 있을 수 있다.

## 해커뉴스가 던진 세 가지 반론

커뮤니티 반응은 한쪽으로 기울지 않았다. 주요 반론 세 가지를 추렸다.

- **도구 브랜드 표기 관행**: "목수에게 전동공구 브랜드를 물으면 입이 마르도록 말한다"는 댓글이 12개 추천을 받았다. 도구명을 숨기는 게 오히려 비투명하다는 주장이다.
- **검증 책임의 비대칭성**: "인간 개발자는 뻔뻔하게 거짓말을 하지 않는다. 무능할 순 있어도"라는 지적이 나왔다. LLM은 환각을 확신 있게 내놓는다는 차이다.
- **계정 분리 실효성**: "주 계정엔 내가 이해한 코드만, 부계정엔 AI 초안만" 전략을 쓰는 개발자가 나타났다. 다만 "회사 업무에서 부계정 쓰면 인사평가 반영이 안 된다"는 현실적 제약도 달렸다.

## 한국 기업은 이미 '표기 의무' 쪽으로 간다

구프타는 투명성이 필요하면 별도 계정이나 README 경고문을 제안했다. 해커뉴스 댓글에서도 "주 계정엔 내가 이해한 코드만, 부계정엔 AI 산출물만" 전략을 쓰는 개발자가 있었다.

반면 국내 사정은 다르다. **네이버·카카오·토스 등 주요 기업은 이미 내부 가이드라인에서 'AI 생성 코드 표기 의무'를 둔다.** 깃허브 한국 커뮤니티에서도 "PR 설명란에 어떤 모델 썼는지 적는 게 관례"라는 목소리가 많다.

본지가 지난해 11월 다룬 '국내 기업 AI 코딩 가이드라인 비교' 기사에서도 삼성전자·LG·쿠팡 모두 'AI 사용 여부·모델명·검증 여부'를 PR 템플릿에 필수 항목으로 넣었다. 구프타의 '공동저자 제거' 주장과 정면으로 배치된다.

| 기업/커뮤니티 | 표기 방식 | 필수 항목 |
|--------------|----------|----------|
| 삼성전자·LG·쿠팡 | PR 템플릿 | 모델명, 사용 목적, 검증 여부 |
| 네이버·카카오·토스 | 내부 위키·가이드라인 | AI 생성 여부, 리뷰어 확인 |
| 깃허브 한국 커뮤니티 | PR 설명란 관례 | 사용 모델, 프롬프트 요약 |

**국내 관행과 구프타의 제안이 엇갈린다. 이 지점이 실무자에게 가장 중요한 차이다.**

구프타 글에는 **법적 책임 소재**와 **팀 단위 협업 규칙**이 빠져 있다. 개인 프로젝트면 몰라도, 회사 저장소에서 공동저자만 뺀다고 책임이 선명해지는 건 아니다. 배포 승인권자·리뷰어·배포 파이프라인까지 맞물려 있다.

## 과거와 지금, 무엇이 달라졌나

구프타 말대로 LLM은 이제 '선택'이 아닌 '생존 도구'다. 회사 업무에서 안 쓰면 도태된다. 사이드 프로젝트는 자율이다. 이 환경 변화가 공동저자 관행 자체를 무의미하게 만들었다.

동시에 책임 소재는 더 선명해졌다. AI가 코드를 짜도 배포 버튼 누르는 건 인간이다. 그 순간부터 법적·도의적 책임은 작성자에게 귀속된다.

## 쉽게 풀어보면

**개발자 구프타가 클로드 코드라는 AI 도구를 깃 커밋의 공동저자에서 빼기로 했다.**  
깃 커밋은 '누가 언제 어떤 코드를 고쳤는지' 기록하는 장부다. 공동저자는 '함께 짰다'는 뜻으로 이름을 올리는 것. LLM(대형언어모델, AI의 일종)은 코드 생성 도구다.

구프타는 1년 전만 해도 "AI 썼다는 걸 알리려고" 공동저자로 올렸다. 지금은 생각이 다르다. AI 쓰기가 당연해진 만큼, 목수가 톱 이름을 가구에 새기지 않듯 도구 이름을 뺀다.

핵심 이유는 책임 회피다. 공동저자가 있으면 버그 터졌을 때 "AI 탓" 하기 쉽다. "내 이름으로 나간 코드면 내가 다 책임진다"는 원칙이다.

대신 실험용 코드엔 별도 계정이나 README(프로젝트 설명 파일)에 "AI 생성 코드 포함, 검증 안 됨" 같은 경고문을 달라고 제안했다. 한국 기업 다수는 이미 내부 규칙으로 'AI 사용 여부 표기'를 의무화하고 있다.

## 나에게 미치는 영향

오늘 바로 적용할 수 있는 세 가지 행동이다.

**챗GPT·클로드·제미나이 등으로 코드 짤 때**  
깃 커밋엔 본인 이름만 남긴다. `git commit --author="내이름 <내이메일>"` 옵션을 쓰거나 전역 설정 `git config --global user.name "내이름"` `git config --global user.email "내이메일"` 을 확인하면 된다. 나중에 버그 터지면 "AI 탓" 못 한다. 최종 검토는 본인이 직접.

**오픈소스 기여할 때**  
README 최상단에 한 줄만 추가하면 된다. 복사해 쓰세요:

> ⚠️ 이 프로젝트에는 AI 생성 코드(Claude 3.5 Sonnet)가 포함돼 있습니다. 핵심 로직은 직접 검증했으나 사용 전 재검토 바랍니다.

별도 계정 쓰려면: 깃허브 설정 → 'Add account' → 새 이메일로 가입 → 로컬에서 `git config user.email "ai계정@메일"` 로 전환 후 커밋. 주 계정엔 이해한 코드만, 부계정엔 AI 초안만 남기는 식이다.

**회사 프로젝트면**  
내부 위키·노션에서 'AI 코딩 가이드라인' 검색. 없다면 팀 리드에게 물어본다. PR(풀 리퀘스트) 설명란에 아래 템플릿을 붙여넣기만 하면 된다:

```
AI 사용: Claude 3.5 Sonnet / GPT-4o
용도: 보일러플레이트 생성, 리팩토링 제안
검증: 단위 테스트 통과, 핵심 로직 직접 리뷰
```

체크리스트: ① 커밋 작성자 본인인가 ② README 경고문 있는가 ③ 회사 규칙 확인했는가 ④ 최종 테스트 직접 돌렸는가.

## 남은 쟁점

공동저자 표기 관행은 팀·프로젝트마다 갈린다. 깃허브 공식 가이드라인도 없다. 해커뉴스 논의처럼 "AI 계정 분리"가 표준이 될지, "공동저자 유지"가 투명성 문화로 남을지 지켜볼 일이다.

핵심은 도구 이름이 아니라 **최종 승인자가 누구냐**다. 그 이름이 곧 책임의 주춧돌이다.
