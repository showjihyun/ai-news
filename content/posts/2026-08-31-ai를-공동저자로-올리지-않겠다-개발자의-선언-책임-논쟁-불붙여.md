## 클로드 코드, 내 커밋에서 이름 뺀다

인도 출신 개발자 구프타가 1년간 유지하던 원칙을 뒤집었다. 자신의 블로그에서 "클로드 코드를 깃 커밋 공동저자에서 빼겠다"고 밝혔다. 해커뉴스에서 18점, 댓글 38개를 모으며 논쟁이 번졌다.

기존 입장은 투명성이었다. LLM 사용 사실을 리뷰어에게 알리려 공동저자 표기를 시작했다. 생각이 바뀌었다. 이제는 LLM 사용이 당연한 시대다.

목수가 톱 이름을 작품에 새기지 않듯, 도구 이름을 커밋에 남길 이유가 없다는 판단이다.

## 책임 회피 수단이 될 수 있다

구프타가 지적한 핵심은 책임 전가다. 공동저자가 있으면 실수 발생 시 "AI가 그랬다"고 변명하기 쉽다. 몇 년 전 구글이나 스택오버플로를 공동저자로 올리지 않았듯, 지금도 마찬가지여야 한다.

그는 "내 이름으로 나가는 작업물이면 온전히 내가 책임진다"고 못 박았다. 버그는 LLM 이전에도 있었고, 검증 의무는 도구가 바뀌어도 변하지 않는다.

이 대목이 걸린다. 도구 탓을 위한 면죄부가 공동저자 표기 뒤에 숨어 있을 수 있다.

## 투명성이 필요하면 별도 계정이나 읽미로

예외도 뒀다. 완전 자동화된 코드나 검증 안 된 실험이라면 AI 전용 계정을 만들거나 README에 경고문을 달라고 제안했다. 해커뉴스 댓글에서도 "주 계정엔 내가 이해한 코드만, 부계정엔 AI 산출물만" 전략을 쓰는 개발자가 있었다.

반론도 만만찮다. "목수는 전동드릴 브랜드를 자랑한다"는 댓글처럼, 도구 공개를 당연시하는 시각도 있다. 오픈소스 프로젝트라면 후속 유지보수자를 위해 AI 사용 여부를 알리는 게 예의라는 주장도 나왔다.

한국 상황은 조금 다르다. 네이버·카카오·토스 등 주요 기업은 이미 내부 가이드라인에서 'AI 생성 코드 표기 의무'를 둔다. 깃허브 한국 커뮤니티에서도 "PR 설명란에 어떤 모델 썼는지 적는 게 관례"라는 목소리가 많다. 본지가 작년 11월 다룬 '국내 기업 AI 코딩 가이드라인 비교' 기사와도 맥이 닿는다.

## 과거와 지금, 무엇이 달라졌나

구프타 말대로 LLM은 이제 '선택'이 아닌 '생존 도구'다. 회사 업무에서 안 쓰면 도태된다. 사이드 프로젝트는 자율이다. 이 환경 변화가 공동저자 관행 자체를 무의미하게 만들었다.

동시에 책임 소재는 더 선명해졌다. AI가 코드를 짜도 배포 버튼 누르는 건 인간이다. 그 순간부터 법적·도의적 책임은 작성자에게 귀속된다.

## 쉽게 풀어보면

개발자 구프타가 클로드 코드라는 AI 도구를 깃 커밋(코드 저장 이력)의 공동저자에서 빼기로 했다. 깃 커밋은 '누가 언제 어떤 코드를 고쳤는지' 기록하는 장부다. 공동저자는 '함께 짰다'는 뜻으로 이름을 올리는 것.

구프타는 1년 전만 해도 "AI 썼다는 걸 알리려고" 공동저자로 올렸다. 지금은 생각이 다르다. AI 쓰기가 당연해진 만큼, 목수가 톱 이름을 가구에 새기지 않듯 도구 이름을 뺀다.

핵심 이유는 책임 회피다. 공동저자가 있으면 버그 터졌을 때 "AI 탓" 하기 쉽다. "내 이름으로 나간 코드면 내가 다 책임진다"는 원칙이다.

대신 실험용 코드엔 별도 계정이나 README(프로젝트 설명 파일)에 "AI 생성 코드 포함, 검증 안 됨" 같은 경고문을 달라고 제안했다. 한국 기업 다수는 이미 내부 규칙으로 'AI 사용 여부 표기'를 의무화하고 있다.

## 나에게 미치는 영향

오늘 바로 적용할 수 있는 세 가지 행동이다.

**챗GPT·클로드·제미나이 등으로 코드 짤 때**
- 깃 커밋엔 본인 이름만 남긴다. `git commit --author="내이름 <내이메일>"` 옵션 확인.
- 나중에 버그 터지면 "AI 탓" 못 한다. 최종 검토는 본인이 직접.

**오픈소스 기여할 때**
- README 상단에 한 줄만 추가: `> ⚠️ 이 프로젝트에는 AI 생성 코드가 포함돼 있습니다. 검토 후 사용하세요.`
- 별도 계정 쓰려면: 깃허브 설정 → 'Add account' → 새 이메일로 가입 → `git config user.email "ai계정@메일"` 로 전환.

**회사 프로젝트면**
- 내부 위키·노션에서 'AI 코딩 가이드라인' 검색. 없다면 팀 리드에게 물어본다.
- PR(풀 리퀘스트) 설명란에 `AI: Claude 3.5 Sonnet 사용, 핵심 로직 직접 검증함` 형식으로 남긴다.

체크리스트: ① 커밋 작성자 본인인가 ② README 경고문 있는가 ③ 회사 규칙 확인했는가 ④ 최종 테스트 직접 돌렸는가.

## 남은 쟁점

공동저자 표기 관행은 팀·프로젝트마다 갈린다. 깃허브 공식 가이드라인도 없다. 해커뉴스 논의처럼 "AI 계정 분리"가 표준이 될지, "공동저자 유지"가 투명성 문화로 남을지 지켜볼 일이다.

핵심은 도구 이름이 아니라 **최종 승인자가 누구냐**다. 그 이름이 곧 책임의 주춧돌이다.
