## 엔비디아가 내놓은 '데이터 통역사' 오토 온톨로지

엔비디아가 기업 데이터베이스(DB) 위에서 자연어 질의를 SQL로 바꿔 실행하는 오픈소스 라이브러리 **오토 온톨로지(Auto Ontology)**를 깃허브에 공개했습니다. 아파치 2.0 라이선스입니다. 이 도구는 기업이 가진 여러 시스템의 메타데이터를 수집해 **'의미 계층(semantic layer)'**을 자동으로 만듭니다. 테이블 이름, 컬럼 정의, 비즈니스 용어, 데이터 계보까지 한곳에 모아 AI 에이전트가 "어디에 무엇이 있고 어떻게 써야 하는지"를 알 수 있게 해줍니다.

공개 시점은 한국 시간 기준 11월 1일 전후로 보입니다. 해커뉴스에서 80점, 댓글 17개를 얻으며 개발자 사이에서 회자됐습니다. 마크테크포스트(MarkTechPost)도 같은 날 소개 기사를 냈습니다.

## 기존 도구와 무엇이 다른가

시맨틱 레이어 자체는 새 개념이 아닙니다. dbt 시맨틱 레이어, 큐브(Cube), 아틀란(Atlan) 등 상용·오픈소스 도구가 이미 존재합니다. 오토 온톨로지의 차별점은 **'자동 생성'과 '에이전트 연동 인터페이스(MCP·CLI·API)'**를 한 패키지에 담았다는 점입니다.

기존 도구는 사람이 온톨로지를 직접 정의·관리하는 경우가 많습니다. 오토 온톨로지는 메타데이터를 집어넣으면 **임베딩과 LLM 추론으로 온톨로지를 자동 구성**합니다. 해커뉴스 댓글에서는 "겟카시스(GetCassis)가 몇 달 전 API 키 없이도 되는 유사 도구를 냈다"는 지적이 나왔습니다. 엔비디아 도구는 **엔비디아 님(NIM) 엔드포인트가 필수**라서 엔비디아 API 키(`nvapi-...`)가 있어야 돌아갑니다.

## 한국에서 바로 쓸 수 있을까

**도커 컴포즈로 로컬 실행은 즉시 가능합니다.** 깃허브 저장소를 클론한 뒤 `.env.example`을 복사해 `DEFAULT_MODELS_API_KEY`(엔비디아 API 키), `CONNECTION_STRINGS`(쿼리할 DB 연결 문자열)만 채우면 `docker compose up -d --build`로 뜹니다. 프론트엔드는 `http://localhost:3000`, 백엔드 API는 `:3001`입니다.

단, **엔비디아 빌드(build.nvidia.com) 회원가입 후 API 키 발급**이 선행돼야 합니다. 한국 리전 호스팅 님 엔드포인트는 아직 별도 안내가 없습니다. 기본값은 `integrate.api.nvidia.com`(글로벌)을 씁니다. 셀프 호스팅 님으로 돌리려면 GPU 서버가 별도 필요합니다.

지원 DB는 **데이터브릭스, 포스트그레스, 스노우플레이크, 덕DB** 네 가지입니다. 한국 기업이 많이 쓰는 오라클, MSSQL, MySQL은 현재 리스트에 없습니다. 커넥터 추가가 오픈소스로 열려 있지만, **현재 외부 기여를 받지 않는 상태**라 엔비디아 측 업데이트를 기다려야 합니다.

## 쉽게 풀어보면

엔비디아가 **'데이터 통역사'**를 오픈소스로 풀었습니다. 기업 안에는 수십 개 DB가 흩어져 있고, 각자 컬럼 이름·단위·정의가 제각각입니다. AI 에이전트가 "작년 매출 얼마야?"라고 물어도 어떤 테이블의 어느 컬럼을, 어떤 필터로 뽑아야 할지 모릅니다.

오토 온톨로지는 이 혼란을 **자동으로 정리해 주는 색인**입니다. 메타데이터를 먹이면 "매출"이 어떤 테이블의 어떤 컬럼인지, 원화인지 달러인지, 세전인지 세후인지를 **온톨로지(지식 그래프)**로 엮어 줍니다. AI 에이전트는 이 색인만 보고도 **정확한 SQL을 짜서 실행**할 수 있게 됩니다.

비유하자면 **도서관 사서가 책마다 '이 책은 어디 선반에 있고, 무슨 주제며, 누가 쓴 건지'를 카드로 정리해 둔 것**과 같습니다. 사서(오토 온톨로지)가 없으면 AI는 도서관 전체를 헤매며 틀린 책을 꺼내 옵니다.

## 나에게 미치는 영향

**데이터 분석가·BI 엔지니어**라면: 지금 쓰는 dbt·큐브·수퍼셋 시맨틱 레이어를 **이 도구로 대체할 수 있는지 PoC(개념 검증) 해볼 만합니다.** 도커로 30분이면 뜨니, 사내 포스트그레스·스노우플레이크 한두 개 연결해 "지난달 매출 TOP 10" 같은 질의를 던져 보세요. 답이 맞으면 점진 이전을 검토하면 됩니다.

**일반 직장인·학생**이라면: 직접 쓸 일은 적습니다. 다만 **챗GPT·클로드·제미나이에 "우리 회사 DB에서 이거 뽑아줘"라고 할 때** 뒤에서 이런 시맨틱 레이어가 작동하면 **환각(잘못된 숫자) 확률이 확 떨어집니다.** 사내에서 "AI로 데이터 뽑아 쓰자" 논의가 나오면 "시맨틱 레이어부터 깔자"는 말로 회의를 이끌 수 있습니다.

**개발자·스타트업**이라면: 아파치 2.0이라 상업적 이용·수정·재배포가 자유롭습니다. **자사 SaaS에 '자연어→SQL' 기능을 얹을 때 베이스라인으로 쓰기 좋습니다.** 단, 엔비디아 님 의존성을 걷어내고 싶은 경우(비용·지연·락인)는 별도 LLM 라우팅 레이어를 짜야 합니다.

## 커뮤니티가 지적한 허점

해커뉴스 스레드에서 개발자들이 **세 가지**를 주로 짚었습니다.

1. **신뢰성 검증 부족**: "에이전트가 5개 사실만 보게 시켜도 안 듣는다. 학습으로 해결 안 됐다는데 이 도구로 되나?"라는 회의론이 큽니다. BIRD 벤치마크 저장소를 따로 뒀지만, 실무 데이터는 벤치마크보다 훨씬 지저분합니다.
2. **엔비디아 락인**: 님 API 키 필수라 **엔비디아 클라우드 비용·가용성·정책 변경 리스크**를 안고 갑니다. 셀프 호스팅 님도 GPU 인프라가 있어야 합니다.
3. **기존 코드베이스 대비 이점 불명확**: "코드베이스에서 스키마·주석·테스트 코드 읽으면 되지, 왜 별도 온톨로지가 필요하냐"는 질문에 명확한 답이 달리지 않았습니다.

마크테크포스트 기사는 **장점만 나열**했고, 해커뉴스에서는 **운영 단점**이 더 많이 나왔습니다. 두 매체 간 온도 차가 뚜렷합니다.

## 아직 확인 안 된 것들

- **한국어 자연어 질의 품질**: 데모·문서가 영문 위주라 한국어 "지난달 매출액 TOP 10" 같은 질의가 얼마나 정확히 SQL로 변환되는지 미확인입니다.
- **대용량 스키마 처리 속도**: 수천 개 테이블·컬럼을 임베딩·동기화하는 데 걸리는 시간·비용 수치가 없습니다.
- **버전 업그레이드·마이그레이션 정책**: 외부 기여를 안 받는 상황에서 버그 픽스·기능 추가 주기가 어떻게 될지 불투명합니다.
- **국내 클라우드(네이버·카카오·KT) 님 호스팅 여부**: 국내 리전 님 엔드포인트가 생기면 지연·데이터 주권 이슈가 풀릴 수 있습니다.

**한 줄 평**: 데모는 잘 뜨지만, **실무 투입 전 '우리 데이터로 환각 안 나는지' 검증부터 하세요.** 엔비디아 님 의존성과 DB 커넥터 제약이 현재 가장 큰 진입 장벽입니다.
