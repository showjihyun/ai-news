## 클라우드 없이 PDF를 AI에게 맡긴다

페이퍼파일럿(PaperPilot)은 파일 하나 서버로 보내지 않고 PDF를 다루는 엔진이다. 러스트로 작성된 단일 코어에서 CLI, MCP 서버, REST API, 브라우저 WASM, 데스크톱 앱까지 다섯 가지 인터페이스를 뽑아낸다. 깃허브 저장소는 공개 10시간 만에 해커뉴스 182점, 긱뉴스 25점을 받았다.

핵심은 **MCP(Model Context Protocol) 지원**이다. 클로드 코드, 코덱스, 키미 코드, 커서 같은 코딩 에이전트가 로컬 `stdio` 서버를 통해 이 엔진을 직접 호출한다. "이 PDF 두 개 합치고 압축해줘" 한 마디면 에이전트가 `paperpilot-mcp`를 띄워 처리하고 결과를 돌려준다. 클라우드 API 키도, 파일 업로드도 필요 없다.

## 쉽게 풀어보면

페이퍼파일럿은 PDF 편집기다. 그런데 설치형 프로그램만이 아니라, **내 컴퓨터에서 돌리는 작은 서버**로도 작동한다. 이 서버는 AI 코딩 도구(클로드 코드, 코덱스 등)가 "도구 호출" 방식으로 부를 수 있게 MCP 표준을 따른다.

비유하자면, 내 책상 서랍에 **전담 비서**를 둔 셈이다. 클라우드에 문서를 맡기지 않고, 비서에게 "이 서류 합쳐", "개인정보 지워", "표만 엑셀로 뽑아" 지시하면 비서가 서랍 안에서 처리하고 결과만 내놓는다. 브라우저 버전(usepaperpilot.com)도 마찬가지다. 네트워크 탭을 열면 파일 업로드 요청이 **단 하나도 없다**. WASM으로 브라우저 탭 안에서 러스트 코드가 그대로 돌아간다.

기능은 합치기·나누기·회전·압축·OCR(순수 러스트 PaddleOCR)·워터마크·서명 검증·개인정보 탐색·딥 새니타이즈·엑셀→JSON/CSV 변환까지 망라한다. 커뮤니티판은 아파치 2.0 라이선스라 상업 이용도 자유롭다. 엔터프라이즈판(SSO, RBAC, 감사 로그, DLP)은 별도 개발 중이다.

## 한국 사용자, 지금 당장 써볼 수 있나

**지금 바로 가능하다.** 세 가지 진입로가 있다.

1. **브라우저**: usepaperpilot.com 접속 → 바로 사용. 한국어 UI는 아직 없지만 메뉴가 직관적이라 무리 없다. 파일은 브라우저 밖으로 나가지 않는다.
2. **CLI·MCP 서버**: 깃허브 릴리스에서 `paperpilot-mcp` 바이너리 내려받아 `claude_desktop_config.json`에 경로만 추가하면 클로드 데스크톱에서 즉시 작동. 코덱스·커서 설정도 문서에 예시가 있다.
3. **로컬 REST API**: `paperpilot serve --port 7823`로 띄우면 `http://localhost:7823/docs`에서 스웨거 문서 보며 테스트 가능.

한글 PDF OCR은 `rten` 기반 PaddleOCR이 담당한다. 영문 위주로 학습된 모델이라 한글 인식률은 검증이 필요하다. 본지가 8일 전 다룬 [왓츠앱 대화 내역, 클로드에서 검색한다… 클라우드플레어 유료 플랜 필요](/posts/2026-10-19-왓츠앱-대화-내역-클로드에서-검색한다-클라우드플레어-유료-플랜-필요/) 도구는 월 몇 달러 유료 플랜이 필수였지만, 페이퍼파일럿은 **로컬 실행이라 추가 비용이 없다**. 무료 한도나 요금제 비교 자체가 불필요한 구조다.

## 기존 유료 도구 대체할 수 있나

아크로뱃 프로나 클라우드 기반 PDF SaaS(스몰피디에프, 아이러브피디에프 등)를 **개인·소규모 업무용으로는 상당 부분 대체 가능**해 보인다. 합치기·압축·회전·페이지 추출·OCR·개인정보 마스킹까지 로컬에서 끝난다. 단, 다음은 아직 불확실하다.

- **깨진 PDF 복구**: 해커뉴스 댓글에서 "lopdf가 손상된 PDF를 잘 못 다룬다"는 지적이 나왔다. 상용 엔진(PDFium, 어도비)은 이 부분이 강점이다.
- **복잡한 레이아웃 OCR**: 표 구조 유지, 다단 인식 등은 순수 러스트 OCR이 어디까지 따라잡았는지 벤치마크만으로는 판단 어렵다.
- **엔터프라이즈 기능**: 감사 로그, 역할 기반 접근 제어, DLP(데이터 유출 방지)는 엔터프라이즈판에만 있다. 사내 규정상 필수라면 커뮤니티판만으로는 부족하다.

## 커뮤니티가 짚은 허점 둘

해커뉴스 스레드에서 두 가지 지적이 반복됐다.

**첫째, "AI 마케팅용 껍데기 아니냐"**. "AI 태그 붙어서 프론트페이지 갔지만 실제 AI 기능은 MCP 연동뿐"이란 회의론이다. 하지만 MCP가 **에이전트에게 로컬 도구 권한을 주는 표준**임을 고려하면, 이 연동 자체가 핵심 기능이다. 본지가 25일 전 다룬 [Figma, MCP 접근 화이트리스트로 전환… Pi 제외에 커뮤니티 반발](/posts/2026-10-02-figma-mcp-접근-화이트리스트로-전환-pi-제외에-커뮤니티-반발/) 사례처럼, MCP 생태계가 닫히는 추세에서 **로컬 퍼스트 MCP 서버**는 오히려 희소해지고 있다.

**둘째, "러스트로 다시 짜기 열풍"**. "기존 검증된 C/C++ 라이브러리 놔두고 러스트로 다시 짜는 게 유행"이란 비판이다. 개발자 입장에선 메모리 안전성·동시성 이득이 크지만, 사용자 입장에선 **깨진 PDF 처리 같은 에지케이스에서 검증된 구현체(PDFium, Poppler) 대비 불리할 수 있다**. 이 부분은 실사용 피드백이 쌓여야 판가름 난다.

## 나에게 미치는 영향

**오늘 해볼 수 있는 것 셋.**

1. **브라우저에서 PDF 합치기·압축하기**: usepaperpilot.com 열어 네트워크 탭 확인하며 파일 하나 안 나가는 걸 직접 본다. 클라우드 PDF 사이트 쓸 때 찝찝했던 사람이라면 즉시 체감 가능하다.
2. **클로드 데스크톱에 MCP 등록해보기**: 릴리스 페이지에서 `paperpilot-mcp` 내려받아 설정 파일에 한 줄 추가. "이 폴더 안 PDF 전부 텍스트로 뽑아줘" 같은 지시로 로컬 자동화 테스트.
3. **로컬 REST API로 스크립트 짜기**: `paperpilot serve` 띄우고 파이썬 `requests`로 배치 처리 파이프라인 만들기. 클라우드 API 키 관리·요금·레이턴시 고민 없이 돌린다.

한글 OCR 품질이 실무급인지, 손상된 PDF를 얼마나 버텨주는지 **내 문서로 직접 테스트해보는 게 가장 빠르다**. 벤치마크 문서(`SYSTEM_BENCHMARK_REPORT.md`)와 `cargo bench --workspace`로 성능도 재현 가능하다.

## 남은 쟁점

- **모바일 지원**: WASM 버전이 모바일 브라우저에서 얼마나 쾌적한지, 터치 UI 최적화 여부는 미확인.
- **임베드 위젯**: `<script src="https://cdn.usepaperpilot.com/embed.js">`로 외부 사이트에 심는 기능은 CDN 의존이 생기므로 완전 로컬 퍼스트와는 거리가 있다. 보안 민감 환경에선 자체 호스팅 필요.
- **한국어 문서·커뮤니티**: 현재 문서는 영어만 있다. 기여 가이드에 "문서 수정"이 좋은 첫 기여로 명시돼 있어 한국어 번역 기여 여지가 크다.

페이퍼파일럿은 **"AI에게 내 파일을 맡기지 않고도 AI에게 PDF 작업을 시킬 수 있다"**는 점을 증명했다. 무료·로컬·오픈소스 세 조건을 동시에 만족하는 PDF 도구는 드물다. 한글 OCR과 깨진 PDF 대응만 실무 수준이면, 개인·소팀은 유료 구독을 해지해도 될 단계로 보인다. 그 검증은 이제 사용자 몫이다.
